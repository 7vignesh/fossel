Fossel is a single Node process that speaks MCP over stdio and keeps everything in one SQLite file. This page covers where data lives, how a repo is identified, what a write does, and how a search is answered.

Storage

All memories live in one SQLite database in WAL mode, at ~/.fossel/memory.db unless FOSSEL_DB_PATH says otherwise. The schema is built by 14 named migrations that run when the database is opened. They are append-only, and a database from an older release is upgraded in place.

TableHolds
memoriesThe notes. One row per memory, with its repo key, type, tags (a JSON array), pin flag, access counters, a normalized copy of the text, and valid_from / valid_to for supersession.
memories_ftsAn FTS5 index over each memory's repo, note and tags, kept in sync by triggers. Tags are searchable.
repo_aliasesMaps alternate repo keys (a folder name, an old key) to the canonical one.
memory_embeddingsOne vector per memory, written only when FOSSEL_EMBEDDINGS is on.
memory_entitiesEntities found in notes: files, packages, services, functions, identifiers and tickets.
memory_file_refsFor each file path a note mentions, the git blob hash of that file when the note was written.
memory_edgesTyped links between memories: fixes, contradicts, supersedes, relates_to.

Deleting a memory removes its embedding, entity and file-reference rows with it. Its edges are not removed: they are closed (given an end time), so the history of a relationship survives.

Repo scoping

Every memory belongs to one repo, and every tool works on one repo at a time. Fossel works out which one like this:

  1. It takes the workspace folder: FOSSEL_WORKSPACE if set, otherwise the server's working directory.
  2. It reads git remote get-url origin and reduces the URL to owner/repo. HTTPS, SSH (ssh:// and git@host:path) and git:// remotes all work, and nested GitLab paths keep every segment. This is the canonical key, for example acme/storefront.
  3. With no usable remote, it falls back to the folder's name.
  4. It records both the canonical key and the folder name as aliases that resolve to the canonical key, so a note saved under either one is found under both.

A tool's repo argument goes through the same alias table. A bare name like storefront resolves to acme/storefront when the last segments match. A name that matches nothing becomes its own repo, so repo: "acme/docs-demo" creates a separate store of memories.

To see the result, call resolve_repo. It returns the canonical key, the aliases, the working directory, the remote, and the source (git-remote, folder, alias or input).

What a write does

There are two ways to save a memory, and they differ on purpose.

  • remember is the everyday tool. It infers a type and up to five tags, writes relative dates out as absolute ones, merges the note into an existing memory when they are near-identical, and tells you about related memories that may conflict.
  • store_context writes exactly what you pass: your type, your tags, your text. No inference, no merging, no conflict notice. It still resolves the repo and grounds relative dates.

After the row is written, remember and store_context also index the note for retrieval: the embedding (if enabled), the entities it names, and a git hash for each file path it mentions. The next page, Memory Lifecycle, walks through the merge, conflict and staleness behavior with recorded examples.

Type and tag inference are keyword heuristics, not a model. A note with no matching signal is typed convention. Pass infer: false to skip inference: the type is then general (unless you pass a type) and only the tags you supply are kept.

How a search is answered

get_context and search_memory share one pipeline. get_context adds pinned and recent memories around it; search_memory returns only matches (plus a fallback, described below).

Step 1: three-tier FTS5 search

The query is lowercased and split on whitespace, /, _, -, . and common punctuation. Any other punctuation and any non-ASCII character is then removed, and tokens shorter than two characters are dropped. So auth.ts becomes auth and ts, and PGRST301 stays one token. Each token is quoted before it reaches FTS5, so query text cannot be read as FTS5 syntax. The search runs in up to three tiers, each reached only if needed:

  1. Exact (AND). Every token must appear in the memory. This is the most precise tier and runs first.
  2. OR. If tier 1 matched nothing and the query has more than one token, any token may match. BM25 ranks the results, and because it already discounts words that appear everywhere, the extra common words in a question add little.
  3. Stemmed prefix. If the first two tiers returned fewer rows than the limit, this tier fills the remaining slots. Each token is trimmed with a conservative suffix strip (ments, ment, ings, ing, ies, ers, er, es, ed, s) and matched as a prefix, so alerts finds alert. A stem is only used if it stays at least four characters long, and it is always a prefix of the original word. This tier appends rows after the exact results. It never reorders them.

Ranking within a tier is BM25 over the repo, note and tags columns. Because non-ASCII characters are removed from the query, café is searched as caf.

Step 2: optional vector search

With FOSSEL_EMBEDDINGS=1, the query is also embedded and compared by cosine similarity with every stored vector for the repo. The built-in embedder uses no model. It hashes each word, each pair of adjacent words, and the four-character pieces of words of six or more characters into a 256-dimension vector. That captures word overlap and shared word parts such as migrate and migration. It does not capture meaning: two sentences with no words in common are not close. Words that are common across the repo's memories are down-weighted in the query, and not in the stored vectors, so adding a memory never forces the others to be re-embedded.

Setting FOSSEL_EMBEDDER_CMD replaces the built-in embedder with a command you provide. Fossel writes text to its standard input and reads a JSON array of numbers from standard output. For many texts it sends one JSON string per line and expects one array per line, so a model loads once per batch. A failing command does not block a write: for that call Fossel uses the built-in embedding instead.

Step 3: entity matches

Entities in the query (file paths, package names, function names, identifiers, ticket ids) are matched against the entities stored with each memory. Memories sharing more entities with the query rank higher.

Step 4: fusing the lists

The ranked lists are combined with weighted Reciprocal Rank Fusion: each list gives an item weight / (60 + rank), and the scores add. The weights are 1.0 for FTS5, 0.8 for vectors, 0.6 for entities and 0.2 for edge neighbours. The vector weight was picked by sweeping it against the committed benchmark, and the repository notes that it has to be re-swept if the embedder changes. Edge neighbours come from one hop along live edges from the top three keyword hits. Superseded memories are excluded from every list.

When embeddings are off, the vector list is empty and the result comes from FTS5, entity matches and edge neighbours.

What get_context adds

The result is assembled in this order: pinned memories, then fused search matches, then the most recent memories to fill any remaining slots up to limit. Near-identical notes are collapsed so the same text never appears twice in one result. Each returned memory has its access count increased, which feeds the stale checks in consolidate_memory, fossel stats and fossel doctor. The same retrieval also runs for the startup resource and for search_memory's fallback, and both count as access too.

In text format, a search match is labelled [match]. A memory without that label was added as pinned or recent context.

What search_memory does differently

It runs the same FTS5 search, then falls back in order: vector search (only if embeddings are on and a repo is known), then pinned and recent memories for the repo. The fallback is only available when a repo is passed, and the result says so in its first line.

Tag filters

get_context and search_memory accept tags and tagMatch. Matching is case-insensitive and compares whole tags. With tagMatch: "or" (the default) a memory needs any listed tag, and with "and" it needs all of them. The filter is applied after search, so when tags are given Fossel fetches a larger candidate pool (the larger of 50 and four times the limit) to avoid returning too few results.

The startup resource

Besides tools, Fossel registers one MCP resource. A client that lists resources when a session starts can show it without any tool call, so the agent sees the top memories before you type anything. The project README says Cursor and Claude Desktop do this; it was not checked here. A client that does not list resources can call get_context as the agent's first action instead. The resource returns the top five pinned and recent memories for the current workspace.
