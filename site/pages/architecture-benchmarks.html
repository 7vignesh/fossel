Fossel searches with SQLite FTS5 in one local file. This page explains that choice, then shows a measured comparison against a dense-embedding baseline built on sqlite-vec and a MiniLM model. The comparison is small and synthetic, and the limits section says exactly how. Read it before quoting any figure.

Why local SQLite FTS5

The project's own design notes state one constraint that drives most decisions: no LLM, no model download, no network at runtime. Search follows from it.

  • One file, no service. Memories, the full-text index and every side table live in a single SQLite database. There is nothing to install, start, keep running or point a client at. The MCP server opens the file and answers.
  • No model to fetch. FTS5 needs no vectors, so there is no embedding model to download, store or load, and no first-run delay waiting for one.
  • The queries agents ask are mostly literal. Error codes, function names, config keys and file paths are tokens, and keyword search finds tokens exactly. This is a design judgment, and the benchmark below tests it on one synthetic corpus. It is not evidence about your repo.
  • Predictable results. The same query over the same data returns the same ranking. Nothing depends on a model version.

A separate vector-database server would add a process to run, a network port, and a way to produce vectors, which means an embedding model. Those are consequences of the design, not measurements. This benchmark did not test a database server. Its dense baseline, sqlite-vec, is a SQLite extension that runs inside the same process, so it is a fairer comparison for a local tool but says nothing about a daemon's latency.

Semantic search is still available. FOSSEL_EMBEDDINGS=1 turns on a built-in vector leg that needs no model, and FOSSEL_EMBEDDER_CMD lets you plug in a real model. See How Fossel Works and CLI & Configuration.

What was compared

One corpus of documents went into three separate SQLite files, and each system answered the same queries.

SystemWhat runs
Fossel 3-tier FTS5searchFts() from src/lib/fts.ts: the exact, OR and stemmed-prefix tiers, ranked by BM25. This is the keyword search Fossel runs by default. It is not a bare bm25() query.
Fossel hybridfetchRepoContext() with FOSSEL_EMBEDDINGS=1: FTS5 plus the built-in 256-dimension hashed vectors, fused with weighted rank fusion, plus entity lookup and the recent-memory backfill.
sqlite-vec + MiniLMA vec0 table with cosine distance over 384-dimension embeddings from Xenova/all-MiniLM-L6-v2 (mean pooling, normalized), computed with @huggingface/transformers in fp32. This is an external baseline. Fossel does not ship it.

What the numbers show

Symbol lookup: FTS5 found every target, the dense baseline did not

The 15 symbol queries are error codes such as PGRST301, function names, config keys and CLI flags. Fossel's FTS5 search ranked the right document first for % of them. The dense baseline did so for %, and had the target in its top three for %.

Of the dense baseline's top-1 misses on symbol queries, ranked a planted decoy first, ranked a generated filler first, and ranked another query's target first. Most of the decoys were the target's own sibling identifier (for example PGRST302 ahead of PGRST301), which is the mistake to expect from an embedding model on near-identical tokens. Not every decoy was a sibling: one was the decoy planted for a different query.

This result is partly built in. Each symbol query is a literal substring of its one target, so a keyword search is expected to find it. The test of the design is the sibling-identifier decoys, which FTS5 passed.

Paraphrase: the dense baseline wins clearly

The 15 paraphrase queries are questions written without the words their answers use. FTS5 had the target in its top 10 for of 15, and in its top three for %. The dense baseline ranked the target first for % and in the top three for %. Fossel's built-in hashed vectors do not close the gap: hybrid mode reached % in the top three, which is one query.

That gap is the reason the FOSSEL_EMBEDDER_CMD hook exists. If your agent asks questions in different words from your notes, a real embedding model helps, and Fossel can use one.

Cost: setup, index build and query time

  • Index build. Building the index for 1,000 documents took ms with FTS5 and ms for the dense baseline. Embedding the documents accounts for ms of that.
  • Model. The dense baseline needs the MB fp32 model, stored outside the database. The first run downloads it over the network, and that time is not in the figures. With the model already cached, loading it took ms. The reference embedder script in the Fossel repository uses a quantized build that its comments put at about 30 MB, which this benchmark did not measure.
  • Query time. searchFts() had a median of ms and a 95th percentile of ms. The dense baseline spent a median of ms embedding the query and ms on the vector search, ms together. Sub-millisecond describes the FTS5 median only.
  • The hybrid path is not cheap. fetchRepoContext() with hashed vectors had a median of ms. It does more than ranking (pinned and recent lookups, entity matching, an access-count write), and its vector leg compares against every stored vector on each query. The no-model default does not pay this.
  • Database size. KB, KB and KB for FTS5, hybrid and sqlite-vec. These are not like for like. The Fossel files carry Fossel's full schema, and the sqlite-vec file holds only a documents table and the vector table.

Method

  • Corpus. The dataset is bench/datasets/scale-1k.ts, generated with a fixed seed so every run builds the same documents. It has 30 hand-written target documents (one per query), 15 hand-written decoys, and 955 template-generated fillers. The fillers are TypeScript signatures, PostgreSQL schemas and errors, stack traces, CLI flags and architecture notes, 191 of each. The 15 decoys are sibling identifiers placed beside the symbol targets.
  • Labels. Each query has exactly one correct document. A test checks that each symbol query occurs, as a substring, only in its target, and that each paraphrase target shares no content words with its query after light stemming.
  • Timing. Each system ran untimed warmup queries, then answered each of the queries once, timed. Percentiles use the nearest-rank method, so the 95th percentile of 30 samples is the 29th-fastest value.
  • Recall. With one relevant document per query, top-1 and top-3 recall are the share of queries whose target was ranked first, or in the first three. Each query is worth about 6.7 points within its category.
  • Embedding. Documents were embedded in batches of and queries one at a time.

Limits

  • The corpus is synthetic. It is generated from templates plus hand-written documents, and the split between symbol and paraphrase queries is deliberate. Neither half predicts accuracy on a real repository's memories.
  • The categories decide the winner. Symbol queries were written to be literal matches, and paraphrase targets were written to share no content words with their queries. A perfect FTS5 score on the first half and a near-zero score on the second are close to guaranteed by construction. The numbers show the size of each effect on this data. They do not show which kind of query your agent asks more often.
  • The query set is small. Thirty queries means one query moves a category by 6.7 points. A different set of 30 could rank the systems differently.
  • One machine, one recorded run. The figures are wall-clock times from a single run on one laptop. A later run on the same machine, which was not committed, measured the dense baseline's index build at about 18.5 seconds and its median embedding-plus-search query at about 5.9 ms, against the recorded 47 seconds and 15.4 ms. Across the five runs made while preparing this page, the FTS5 median ranged from 0.62 to 1.18 ms. Timings vary a lot between runs here, so treat the latencies as an order of magnitude, not as a specification.
  • The dataset was revised after the first run. The first version gave every paraphrase query a decoy that reused the query's own words. All three systems, the dense one included, ranked those decoys first, so paraphrase top-1 was 0% for every system and told nothing. Those 15 decoys were replaced with generic documents. That change was made after seeing results, and it raises the dense baseline's paraphrase score.
  • Dense search was measured alone. The baseline is not fused with keyword search, and Fossel was not run with an external embedder, which is the setup that combines both. This benchmark says nothing about that combination.
  • No database server was tested. See the first section.

Reproduce it

From a clone of the repository, with Node 20 or newer:

npm ci npm run bench:neural

The first run downloads the model into bench/.cache/, which is ignored by git. The script prints the tables and writes bench/results/neural-compare.json. It is not part of npm run ci, because it needs the network on first use and its timings are not stable enough to gate on. The recall figures are deterministic and reproduced exactly across runs here. The latencies were not.
