A memory is created, may be merged with a near-duplicate, may be flagged against a related one, can be retired without being erased, and can be marked stale when the code it mentions changes. This page follows one memory through those stages. Every response shown is recorded from the real server by npm run docs:snapshot.

1. Create

remember saves a note. With no type or tags given, Fossel infers them and reports what it chose.

You can set the type, the tags, or both. Fossel merges your tags with the inferred ones and keeps at most five.

The six types are convention, bug_fix, reviewer_pattern, decision, issue and general.

Relative dates are written out

A note that says "last week" will be wrong in a month. When a note contains a relative date, Fossel appends the absolute date in parentheses and keeps your wording.

Storing exactly what you give

infer: false on remember skips type and tag inference. store_context goes further: it never merges and never raises a conflict notice.

2. Merge near-duplicates

Saying the same thing twice should not create two memories. On every remember, Fossel compares the new note with the repo's 200 most recently updated memories. If one scores 0.82 or higher, the new note merges into it instead of being stored.

The score blends word overlap (55%) with overlap of three-character pieces of the text (45%), after lowercasing and removing punctuation. A note that matches an existing one exactly after that cleanup is found immediately, without scoring.

On a merge, the longer of the two notes is kept, the tags are combined, the existing type is kept unless you passed one, and the change is recorded in the memory's history.

3. Flag related and conflicting memories

A note that changes an earlier decision is similar to the old one, but not similar enough to merge. For notes that score between 0.28 and 0.82 against existing memories, remember lists up to the three closest in its reply. If exactly one of the two notes contains a replacement or negation cue (such as no longer, not, never, instead, replaced, deprecated or migrated), the entry is marked ⚠ may contradict/supersede.

Fossel does not decide anything here. It cannot read meaning, so it reports the candidates and leaves the call to the agent, which can then use update_memory, supersede_memory or delete_memory. The same candidates are saved as edges (contradicts when flagged, relates_to otherwise), so the link survives after the reply is gone.

4. Revise

update_memory changes a memory's text, its type, or both. It re-indexes the new text, so search, entities and file references follow the edit.

Pinning moves a memory to the top of get_context results.

5. Retire, don't erase

supersede_memory ends a memory's life without deleting it. The row stays in the database with an end time and a history entry, and it stops appearing in every live search and listing. If you name its replacement, Fossel also records a supersedes edge when both are in the same repo.

A superseded memory can no longer be looked up by id. Tools that take an id report it as not found, and that includes calling supersede_memory on it a second time. Only export_memories and the repo counts still see it.

Use delete_memory when the memory was simply wrong and should leave no trace. Deleting removes the row for good, along with its embedding, entities and file references. Its edges are closed, not removed.

6. Clean up

Two tools help keep a repo tidy. Both leave the decision to you.

consolidate_memory is read-only. It reports memories that look stale (never returned by a context retrieval, not pinned, and not updated for more than stale_days days, default 90), pairs that look redundant (similarity of 0.70 or more), and pairs where one note carries a negation cue that the other lacks (similarity from 0.28 up to 0.70). The stale check covers every live memory. The two pair checks look at the 100 most recently updated, and the report stops at max_candidates entries (default 20).

dedupe_repo merges near-duplicates in bulk. By default it only prints a plan. Pass apply: true to carry it out. Memories of different types are never merged. The memory that is kept is the more recently updated one, and it ends up pinned if either of the two was pinned. The default threshold is 0.85, stricter than the 0.82 that remember uses.

7. Detect code drift

A memory that says "the auth middleware in src/auth.ts rejects expired tokens" goes wrong when that file changes. When you save a note inside a git repository, Fossel finds the file paths in it (names ending in a recognized code or config extension) and records each file's git blob hash at that moment.

On every get_context, Fossel compares those hashes with the files now. A memory whose file has changed gets a marker: ⚠ may be stale, and has uncommitted changes when the edit is not committed yet. A path that git cannot resolve (an untracked, ignored or non-existent file) gets a different marker, ⓘ unverified, because it was never checked, and the absence of a warning there means nothing.

Both markers are advisories. Fossel does not hide or rewrite the memory. Outside a git repository nothing is recorded and nothing is flagged.

Only get_context shows these markers. search_memory and get_repo_context do not. fossel stats reports a count of memories whose files have drifted.

8. Move data in and out

export_memories writes a versioned JSON envelope of memories, repo aliases and edges. It includes superseded memories. It leaves out embeddings, which are rebuilt on import so the file stays small and does not depend on any model. With no path the envelope is the response. With a path the envelope is written to a file and the response is a one-line summary. The path must resolve inside the workspace.

import_memories is additive and idempotent. A memory whose id already exists is skipped and never overwritten, so importing the same file twice changes nothing. There is no replace mode. To start from nothing, delete the database file. Import re-derives embeddings, entities and file references for what it adds.
